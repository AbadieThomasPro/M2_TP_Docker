Communications et ordre de démarrage Schéma des communications · Dépendances entre conteneurs

Chemin d'une requête : le navigateur ne connaît que le front, qui relaie vers la gateway, qui relaie vers le back.

sequenceDiagram
  autonumber
  actor N as Navigateur
  participant F as front (Node)
  participant G as gateway (nginx)
  participant B as back (Node)
  N->>F: GET / sur 127.0.0.1:8080
  F-->>N: application Angular (HTML, JS, CSS)
  N->>F: GET /api/files (même origine, pas de CORS)
  F->>G: relais vers http://gateway/api/files (interne-front)
  G->>B: proxy_pass vers http://back:3000/api/files (interne-back)
  B-->>G: 200 [fichiers non expirés]
  G-->>F: 200
  F-->>N: 200, liste affichée
  Note over N,G: Envoi plus gros que MAX_UPLOAD_MB : la gateway répond 413 sans contacter le back
requête réponse ① à ⑧ : ordre des échanges

Ordre de démarrage (depends_on: condition: service_healthy)

1 · back healthy → 2 · gateway + 2 · cleaner healthy → 3 · front
ServiceAttendHealthcheckPourquoi cet ordre
back–GET /healthPremier : c'est lui qui initialise les droits du volume
gatewayback healthyGET /health sur 127.0.0.1Sans back prêt, elle répondrait 502 à chaque appel (testé)
cleanerback healthyDate de la dernière passe (pas de réseau)Le premier conteneur qui monte un volume neuf y copie ses droits : le back doit passer avant
frontgateway healthyGET /La page n'est servie qu'une fois toute la chaîne vers l'API prête

Healthchecks définis dans chaque Dockerfile ; en Swarm (pas de depends_on), l'image du cleaner contient aussi le dossier du volume : l'ordre n'a plus d'importance (vérifié).

Entrypoints et arguments Entrypoints · Arguments attendus · Traduits dans le compose

Entrypoints choisis (toujours en forme exec)

ImageENTRYPOINT / CMDPourquoi
front, back["/sbin/tini","--"] + ["node","…"]Node en PID 1 ignore SIGTERM : tini le relaie et nettoie les zombies. Sans shell intermédiaire
gateway["/entrypoint.sh"] + ["nginx","-g","daemon off;",…]Modèle « wrapper d'init » : le script génère la config depuis l'ENV puis exec "$@" → nginx devient PID 1. CMD remplaçable (nginx -t). STOPSIGNAL SIGQUIT : finit les requêtes en cours
cleaner, autoscaler["/usr/local/bin/…sh"]Script shell conçu pour être PID 1 : il gère lui-même SIGTERM (trap), pas besoin de tini

Arguments : ARG (build) → ENV (défaut de l'image) → .env (déploiement)

NiveauRôleTraduction dans le compose

ENVDéfaut dans l'image : l'image démarre seule, sans composeenvironment: ← .env (changer une valeur = sans rebuild)

Limites connues

Un seul nœud SwarmPlusieurs machines demanderaient un registre (registry:2 vient du Hub) et un stockage partagé
Rafale d'envois20 envois de 40 Mo : front à 99 % de sa mémoire ; la rafale (~15 s) est plus rapide que l'autoscaler (~40 s)

Rejouer les tests : outil de charge Bench/ (alpine + ab) ; démonstration de l'autoscaling en une commande : ./Bench/run-autoscale-demo.sh (mode d'emploi : docs/tester-la-charge.md).
